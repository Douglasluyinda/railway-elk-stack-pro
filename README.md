# ELK Stack for Railway

Elasticsearch, Logstash and Kibana as **three separate services** on Railway's **private network**.
Only Kibana has a public domain. Security is on, secrets are generated at deploy time, and log
indices are deleted after a configurable number of days.

```
your app ──(private HTTP, basic auth)──> Logstash ──(least-privilege writer)──> Elasticsearch
                                                                                     ^
browser ──(HTTPS + login)──> Kibana ─────────────────(private HTTP)─────────────────┘
```

> **Status:** the scripts and configs pass the checks listed under [What is verified](#what-is-verified).
> The stack has **not yet been deployed on Railway** and the Elastic images have not been run by the
> author. Deploy once and walk through [Verify the deployment](#verify-the-deployment) before publishing.

## What you get

| Service | Image | Public? | Volume | Notes |
| --- | --- | --- | --- | --- |
| Elasticsearch | `elasticsearch:8.19.21` | No | `/usr/share/elasticsearch/data` | Single node, security on, creates the log writer user, retention policy and index template on start |
| Logstash | `logstash:8.19.21` | No | none | Authenticated JSON intake on `:8080`, writes to `railway-logs-YYYY.MM.dd` |
| Kibana | `kibana:8.19.21` | **Yes** | none | Log in as `elastic`; saved objects live in Elasticsearch |

Versions are build arguments (`ELASTIC_VERSION`) in each Dockerfile. Keep all three on the same version.

## Deploy

Use the template's deploy button once it is published, or build it yourself from this repo by following
[TEMPLATE.md](TEMPLATE.md) (exact service names, root directories, variables and volume).

To try it locally first: `cp .env.example .env`, fill in the values, then `docker compose up --build`
(about 3 GB of free RAM).

## Verify the deployment

1. **Elasticsearch** deploy logs should end with `[railway-es-setup] setup complete`.
2. Open Kibana's public URL and log in as `elastic` with the `ELASTIC_PASSWORD` value from the
   Elasticsearch service's Variables tab.
3. From another service in the **same project and environment**, send a test event:

   ```bash
   curl --fail-with-body --user "shipper:$LOGSTASH_PASSWORD" \
     -H 'Content-Type: application/json' "$LOGSTASH_URL" \
     -d '{"message":"hello from Railway","service":"my-app","level":"info"}'
   ```

   with these variables on the sending service:

   ```text
   LOGSTASH_URL=http://${{Logstash.RAILWAY_PRIVATE_DOMAIN}}:8080
   LOGSTASH_PASSWORD=${{Logstash.INPUT_PASSWORD}}
   ```

4. In Kibana: **Stack Management → Data Views → Create data view**, index pattern `railway-logs-*`,
   time field `@timestamp`. Then open **Discover** and search for `hello from Railway`.

An HTTP 200 from Logstash means the event was accepted, not that it was indexed. Check Discover.
The private URL only works from inside the same Railway environment, not from your laptop.

## Configuration

| Variable | Service | Default | Purpose |
| --- | --- | --- | --- |
| `LOG_RETENTION_DAYS` | Elasticsearch | `14` | Days before `railway-logs-*` indices are deleted |
| `ES_JAVA_OPTS` | Elasticsearch | `-Xms512m -Xmx512m` | JVM heap; raise it for more data |
| `LS_JAVA_OPTS` | Logstash | `-Xms256m -Xmx256m` | JVM heap |

All passwords and encryption keys are generated by the template. See [TEMPLATE.md](TEMPLATE.md) for the full list.
Passwords must not contain double quotes or backslashes (`setup.sh` rejects them).

## Security notes

- Never add a public domain to Elasticsearch or Logstash. Elasticsearch HTTP is plain (no TLS) because
  traffic stays inside Railway's encrypted private network; its login is the only barrier.
- Logstash's intake requires basic auth, but anything in the same environment that knows `INPUT_PASSWORD`
  can write logs. Logstash's monitoring API (`:9600`) is unauthenticated on the private network.
- Logstash writes with a dedicated `logstash_writer` user that can only create and index into `railway-logs-*`.
- The pipeline removes the `headers` field so the intake credentials are never indexed.
- Keep the Kibana encryption keys stable. Changing them invalidates saved objects and sessions.

## Limitations

- **Single node.** Volumes give persistence, not high availability or backups. Take snapshots before upgrades.
- Railway platform logs are not collected automatically; applications must send events to Logstash.
- Expect roughly 2.5 to 3.5 GB of RAM in total. This is an estimate, not a measurement. For reference, another
  published ELK template reports a 3.2 GB idle sample.
- `node.store.allow_mmap: false` is set so Elasticsearch does not depend on the host's `vm.max_map_count`.
  It costs some search speed. Remove it if you know your host allows 262144 or more.
- No Railway healthchecks are configured. Kibana's `/api/status` needs authentication by default, so a
  healthcheck would fail. `/login` may work, but that is untested.
- Free and Trial plan volume limits (0.5 GB) are too small for real log volumes.

## What is verified

Run `bash scripts/validate.sh` (no Docker or network needed).

| Checked | How |
| --- | --- |
| Shell syntax and shellcheck | `bash -n`, `shellcheck` |
| `railway.json` and YAML files parse | Python `json` and `yaml` |
| `setup.sh` call order, JSON bodies, retries, input validation, credentials kept off the command line | 16 tests against a fake `curl` |
| `entrypoint.sh` volume chown and privilege drop | 5 tests against fake `id`, `stat`, `chown`, `setpriv`, `runuser` |
| Logstash pipeline structure | Brace and section check only |

**Not verified** (the sandbox could not reach Elastic's registries, and nothing was deployed):

- Docker builds, and that tag `8.19.21` exists for all three images.
- Elasticsearch starting with the config and volume ownership handling, including the `setpriv` privilege drop.
- Binding to `::` for Elasticsearch, Kibana, and the Logstash input and API on Railway's private network.
- The Logstash pipeline passing `logstash --config.test_and_exit`, and the `elasticsearch` output options.
- Kibana connecting as `kibana_system` after `setup.sh` sets its password.
- Whether canvas grouping is preserved in the published template.
- Real cost, restart and upgrade behaviour.

## Upgrading

Change `ELASTIC_VERSION` in all three Dockerfiles together and redeploy Elasticsearch first. Never downgrade
Elasticsearch against upgraded data; restore from a snapshot into a separate stack instead.
